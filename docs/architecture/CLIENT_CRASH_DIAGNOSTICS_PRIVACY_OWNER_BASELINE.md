# Client Crash Diagnostics Privacy Owner Baseline

- Status: Owner-accepted pre-contract baseline
- Date: 2026-08-07
- Decision owner: Oteryn project owner
- Coordination ID: `OTV2-NATIVE-FOUNDATION`
- Applies to: native-client crash diagnostics, privacy settings, privacy-policy disclosure, diagnostics ingestion and later client / Platform / Game Intelligence contracts
- Related: `DISCONNECT_LIVENESS_AND_CRASH_EVIDENCE_OWNER_BASELINE.md`, ADR-0006

## Purpose

Record the owner-accepted privacy boundary for automatic native-client crash diagnostics.

This is architecture only. It does not authorize runtime, client, Platform, telemetry-backend, persistence or production implementation.

## Owner-accepted default and user control

Automatic submission of eligible client crash diagnostics is enabled by default, but the native client must expose a clear global privacy setting that allows the user to disable client-originated diagnostic/crash-report uploads.

The setting applies globally to automatic client diagnostics rather than asking for confirmation after every individual crash.

Conceptually:

```text
client_diagnostics_upload = enabled   -> eligible bounded crash packages may upload automatically
client_diagnostics_upload = disabled  -> client-originated diagnostic/crash packages must not be uploaded
```

A user who disables the setting must not be prevented from starting the client, authenticating or playing solely because optional client diagnostics are disabled.

## Privacy-policy disclosure

The applicable privacy notice/policy must clearly disclose, in understandable language, at least:

- that automatic client crash diagnostics are enabled by default;
- how the user disables or re-enables them;
- the purposes for which diagnostics are processed, including stability, regression, compatibility, security and incident investigation;
- the categories of diagnostic data that may be collected;
- the categories explicitly excluded from crash packages, including reusable credentials, authentication tokens, private chat content and unrelated user files;
- how diagnostic reports may be correlated with bounded session/build/world/node evidence where necessary for incident analysis;
- applicable retention/deletion or anonymization rules once those contracts are finalized;
- who or which operator/developer/security roles may access the data;
- whether automated analysis, including read-only AI-assisted investigation, may be used;
- that diagnostic analysis itself does not automatically ban the player or mutate authoritative gameplay state.

The final legal/privacy text and lawful-basis/consent treatment remain subject to the jurisdictions in which Oteryn is operated and must be reviewed separately before production release. This architecture baseline does not itself make a legal-compliance determination.

## Opt-out behavior

When client diagnostic upload is disabled:

- no new client-originated crash package may be transmitted automatically;
- already queued but not yet transmitted crash packages must not be uploaded while the setting remains disabled;
- background retry/backoff for client diagnostic uploads must stop while disabled;
- disabling diagnostics must not weaken server-authoritative liveness, disconnect protection, session fencing or gameplay integrity;
- the client must not silently re-enable diagnostics after update, restart, relogin or settings migration unless a separately accepted migration/privacy requirement explicitly requires a new choice;
- the setting must be represented durably and predictably so the user's choice survives normal client restarts.

Whether an opted-out user's existing local-only crash package is deleted immediately or retained locally for manual export/troubleshooting remains a later client/privacy retention decision. In either case it must not be uploaded while opt-out is active.

## Client diagnostics versus server-side operational evidence

The privacy setting governs telemetry and crash evidence originating from the user's native client. It does not mean the player can disable authoritative or operational evidence generated by Oteryn services themselves.

Server-side evidence may still be required for purposes such as:

- authentication/session security;
- authoritative gameplay correctness;
- anti-duplication and transaction audit;
- GameNode/runtime health and crash recovery;
- abuse/security investigation;
- infrastructure incident analysis;
- legally or operationally required audit/retention.

Those server-side evidence classes remain governed by ADR-0006 and later privacy/retention/security contracts. They must use data minimization, access control, defined retention and pseudonymization where appropriate.

The UI and privacy policy must not misleadingly present the client diagnostics switch as a switch that disables all server logging or all service-side processing.

## Anti-abuse independence from client diagnostics

The owner explicitly accepts that abuse detection and security investigation must **not depend on optional client-originated diagnostics**.

A user may disable client crash diagnostics for privacy reasons. That choice does not reduce the server's ability or authority to retain and analyse required gameplay/security evidence generated by Oteryn services.

Therefore:

- opt-out from client diagnostics must not disable or suppress server-side security/gameplay evidence;
- opt-out must not prevent server-side recording of liveness transitions, disconnect-protection activation, reconnects, transport generations, combat/PZ state, risk context, encounter context, repeated disconnect patterns or other evidence accepted by later security/gameplay contracts;
- server-side anti-abuse analysis must remain capable of detecting suspicious patterns even when no client crash report exists;
- missing client diagnostics may reduce diagnostic certainty about *why* a client failed, but it must not make the corresponding server-observed gameplay incident invisible;
- client crash evidence, when available, is corroborating diagnostic evidence rather than a prerequisite for an abuse case.

A representative server-observable pattern may be conceptually analysed as:

```text
low HP / high combat risk
    -> loss of server-authoritative liveness
    -> disconnect protection
    -> reconnect / re-entry protection
    -> heal / escape
    -> repeated similar sequence across incidents
```

Such a pattern may warrant investigation based on server-side evidence alone, subject to the accepted telemetry, human-review and enforcement-policy boundaries.

## Privacy choice is not suspicion evidence

The owner explicitly rejects treating the privacy setting itself as evidence of abuse.

The following are binding invariants:

- disabling client diagnostics must not itself increase an abuse score, suspicion score, risk score or enforcement priority;
- enabling diagnostics must not itself lower such scores or create a presumption of innocence;
- security decisions must be based on relevant behavior/evidence, not on whether the user exercised a privacy control;
- Game Intelligence may record that client diagnostic evidence is unavailable only as an evidence-availability fact, not as adverse behavioral evidence;
- human reviewers must not treat the opt-out itself as proof of concealment or malicious intent.

This preserves the user's privacy choice without creating a blind spot in server-authoritative anti-abuse analysis.

## Data-minimization boundary

Even when automatic client diagnostics are enabled:

- collection is allowlist-based rather than collect-everything-and-filter-later;
- local redaction/filtering occurs before transmission;
- report and attachment sizes are hard-bounded;
- arbitrary user files and unrestricted log directories are prohibited;
- secrets and reusable credentials are prohibited;
- unrelated personal data is prohibited;
- private chat content is prohibited;
- client diagnostic payloads remain untrusted input and are validated at ingestion;
- diagnostic collection must be proportionate to its documented purpose.

## Required future tests

Future implementation must prove at minimum:

1. client crash-report upload is enabled by default under the accepted product policy;
2. disabling the global diagnostics setting prevents automatic client crash-package upload;
3. pending retries stop while diagnostics are disabled;
4. the opt-out survives ordinary restart/update/settings persistence paths;
5. optional diagnostics being disabled cannot block normal startup or gameplay admission;
6. enabling diagnostics does not bypass redaction, allowlists or size limits;
7. the client privacy switch does not disable required server-side authoritative/security evidence;
8. server-side abuse/security analysis remains functional when client diagnostics are disabled or absent;
9. disabling client diagnostics does not itself raise an abuse/suspicion/risk score or otherwise count as adverse evidence;
10. UI/privacy documentation accurately distinguishes client-originated optional diagnostics from server-side operational/audit evidence.

## Programme effect

Accepted now:

```text
client crash diagnostics -> automatic by default
user -> global privacy opt-out available
opt-out -> no automatic client diagnostic upload
per-crash confirmation -> not required while diagnostics are enabled
opt-out persists across normal restart/update/settings persistence
client opt-out != disabling authoritative/server-side operational evidence
server-side anti-abuse/security evidence remains mandatory and independent of client diagnostics
absence of client crash report != absence of server-side incident evidence
client diagnostics opt-out itself != suspicious behavior / abuse evidence / score increase
privacy policy -> must transparently describe collection, purpose, controls, access, correlation and retention
AI-assisted diagnostics -> disclosed where applicable, remains read-only/non-authoritative
```

No runtime, client, Platform, persistence, telemetry-backend or production implementation is authorized by this baseline.
