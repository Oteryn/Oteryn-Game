## Reading the inventory

The scope is every immediate `modules/client_*` and `modules/game_*` directory at the pin: 11 client modules and 58 game modules, 69 rows. The unsuffixed `modules/client`, `corelib`, `gamelib`, `modulelib`, `startup` and `updater` are outside that requested glob. Supporting style/protocol files are used only to interpret inheritance and wire behavior.

- **PROVEN reference observations:** OTUI/HTML file names, widget IDs, Lua callback/action identifiers and literal key defaults are read from the pinned tree. OTUI paths and HTML paths in a row are relative to `modules/<module>/`. Some modules now use HTML instead of OTUI; absence of an OTUI window does not mean absence of a panel. Shared miniwindow behavior is in `data/styles/30-miniwindow.otui` and `modules/corelib/ui/uiminiwindow.lua`. “Fixed template” means no explicit resize/minimise affordance observed, not an immutable OS size. A modal may use a floating window implementation; actual input capture must be verified during wiring.
- **Protocol notation:** `S` means received server opcode, `C` means sent client opcode. Symbols/numbers are OTClient reference values, traced through `src/client/game.cpp`, `protocolgamesend.cpp`, `protocolgameparse.cpp`, `protocolcodes.h` and Lua singleton bindings in `luafunctions.cpp`; they are **not Oteryn opcodes**. Lists cover directly traced Lua calls/callbacks and direct OTUI gameplay button calls; indirect shared-controller/widget actions may add traffic. No literal opcode in a Lua module is not evidence of no protocol use. Version gates and C++ multiplexing remain relevant; do not transplant these bytes. `ExtendedIds.Locale = 1` and shop subopcode `201` are custom reference extensions.
- **Behavior notation:** `E` lists consumed domain/session callbacks (UI callbacks omitted), `A` lists outgoing gameplay actions (including direct OTUI handlers), `K` lists literal key defaults and local navigation keys. Session start/end clears/restores module-local state where hooked. Empty `K` means no literal default found in the module; configurable/shared bindings may still exist. Event callback names denote observations, not proof the target server emits them.
- **Oteryn mapping is DERIVED:** numeric IDs and canonical slugs come from `docs/contracts/protocol-oteryn/v1/registry/capabilities/*.json`; command numbers are a separate namespace. `E`/`U` after a feature mean its current `registrations/handlers.json` is implemented/unsupported. `D` means an existing directory without that handler fragment. A directory or panel fragment alone does not prove a playable panel. Paths prefixed `features/` are relative to `crates/client-ui/src/`; runtime/domain counterparts belong in their own crates under the same feature name. Existing app adapters under `apps/client/src/features/` are not permission to expand app-level dispatch.
- **Proposed paths:** `P features/local-*/` is only for local UI. `P features/<pending-id>-*/` is a notation for a server feature awaiting an accepted numeric allocation, not a valid directory to create. Forge-creature `0104` does not allocate a forge-operation panel; character-info `0097` does not allocate wheel/proficiency mutation commands.
- **Server status is bounded static evidence:** “exists” means the named code is on the baseline, not that every Global action is complete or offered. The capability ledger below preserves static offer flags and summarizes material gates. Runtime admission/content gates can offer capabilities whose registry flag is false. Check live generated descriptors and negotiated capabilities before step 8. This docs-only task ran no server qualification.
- **Global comparison is UNKNOWN:** no Global screenshots/session were supplied. Every row says “verify vs Global”; specific reference-only risks are called out without asserting an unverified difference. No graphics, hotkey parity or pixel fidelity is approved by this inventory.

- **Inventory/containers and NPC trade:** durable item movement/equipment/tree and trade routes exist. `0012`, `0014`, `0081` and related item extensions are bundle-gated. NPC dialogue uses `0003`; modern shop/sell-all extends it through `0081`, not an invented shop capability.
- **Console/party/VIP:** chat, guild/private channels and channel-list owners exist; party actions are `0042` and visible party skull metadata is a separately gated `0134`. There is no `game_party` module in this reference: party menus live in `game_interface`, shields in creature/battle views, and party hunt numbers in `game_analyser`. VIP `0043` owns durable list/consent/query only; its registry explicitly excludes presence/status notifications. Do not promise reference `onVipStateChange` behavior from that capability.
- **Skills/cooldowns/analysers:** character-info `0097` supports query projections; progression/vitals also come through existing session state, not a newly allocated “skills” capability. Presentation publisher/cooldown code exists in `spell_presentation_publisher.rs` and `spell_presentation_cooldowns.rs` under `crates/gameplay/dispatch/src/gameplay_transport/`; the `0023` registry retains an activation/measurement gate. `0010` still says its first emitter is required, so complete hunt graphs/party numbers are not proven. `0117` only proves the boss cooldown query (`boss_encounter.rs`), not Bosstiary progression or reward delivery. Training `0054` is provisional, shipped data disabled, with explicit runtime opt-in; never silently enable it for a skills button.
- **Quest/market/stash/daily reward:** quest log `0016`, market `0063`, stash `0062` and daily reward `0032` have dispatch owners named above.
