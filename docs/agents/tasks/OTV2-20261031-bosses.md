## Shared Activity handoff API

The shared durable owner is `durability::activity_handoff::ActivityHandoffOwner`.
Boss rooms and Soulpit use this owner; there is no second allocation, session or
claim writer. The public signatures, with the existing public error alias, are:

```rust
pub async fn enter(
    &self,
    authority: &ReconciledCharacterAuthority<'_, '_>,
    node: &NodeIncarnationProof,
    request: ActivityEnterRequest,
) -> Result<ActivityEnterOutcome, ActivityHandoffError>;

pub async fn return_participant(
    &self,
    authority: &ReconciledCharacterAuthority<'_, '_>,
    node: &NodeIncarnationProof,
    request: ActivityReturnRequest,
) -> Result<ActivityReturnOutcome, ActivityHandoffError>;

pub async fn recover(
    &self,
    authority: &ReconciledCharacterAuthority<'_, '_>,
    node: &NodeIncarnationProof,
    request: ActivityRecoveryRequest,
) -> Result<ActivityRecoveryOutcome, ActivityHandoffError>;
```

`ActivityHandoffError` aliases `DurabilityError`; `ActivityRecoveryRequest` and
`ActivityRecoveryOutcome` alias the corresponding return types.
`enter_boss_room` has the same argument and result types as `enter` and adds the
boss catalogue, lever rules and per-participant cooldowns in the same transaction.
Soulpit uses the generic `enter`. Entry takes a group from one current Channel
into a fresh Instance in the same World; return goes from that Instance to the
retained origin Channel. These APIs do not authorize Instance-to-Instance travel.

Entry consumes a fresh, independently ready control allocation for the exact
Instance scope, generation and assignment revision. It retains qualified content
digests, the current participant fences, fresh destination sessions/transports,
authored entry/exit cells and each participant's original selected capabilities.
Runtime code creates no control grant, assignment or readiness publication.
Return issues another fresh session and advances the Character lease. Its
`command_id: Option<u64>` contains a real client command or is absent for a
separately proven server occurrence; it never fabricates command zero.

`recover` is the departed-owner return path. It forces the owner-loss cause and
an offline destination, proves that the Instance owner is lost and that the
origin Channel owner is current, and retains any proven death/pending-respawn
obligation. `recover_departed_death` first resumes incomplete selected death-item
causes through their existing writer under the exact Instance `SpellLanePermit`.
It uses the sealed `DepartedActivityDeath` proof from `read_departed_death`.

Lost acknowledgement while the native owner still exists is separate:
`transfer_recovery(session)` returns an inert current routing projection;
`recover_transfer` requires registered credential evidence, current claims and
scope authority, a fresh transport and the retained capability selection. It
keeps the same actual actor/session and advances connection generation. The same
candidate/nonce/transport can reconcile an uncertain commit. `note_transfer_input`
closes unused-handoff recovery before the first real command; a genuine recorded
owning loss uses the existing same-session reconnect owner.

An `Entered`, `Returned` or replay receipt is historical evidence, not current
native authority. Composition reserves the exact destination, retains physical
and spell-state tokens through SQL uncertainty, and installs both under the
runtime locks only after the durable outcome is known. Commands then resolve the
current admitted owner from the shared scoped registry. Domain 99 with capability
117 publishes the fresh-session scope barrier. Native removal additionally waits
for `retirement_ready`, drained kill obligations, no players/reservations and
`retire_activity_ground_step` returning `Complete`.

Source: `crates/gameplay/durability/src/durability/activity_handoff.rs` and its
`returning.rs`, `transfer_recovery.rs`, `departed_death.rs` and `retirement.rs`
modules; native composition is in `gameplay_transport/native_activity.rs`,
`native_activity_return.rs` and `activity_runtime.rs`. This API description makes
no final-head test claim.
