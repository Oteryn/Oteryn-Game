## Plan (written before coding)

1. **Content (D114)**: mark `oteryn:item.registry.i00002752` (backpack) `semantics.equipment` as
   `KNOWN` with one complete equip pattern (`pattern_id=1`, `primary_slot=KNOWN(CONTAINER)`,
   every other pattern field `UNKNOWN`), following the existing `ReferenceItemField`/
   `ProjectReferenceRecord::Item` JSON convention. Replaces B3-1's "test-only fixture backpack"
   gap for the one definition the owner approved; `container.capacity = 20` is already `KNOWN`.
2. **Content-binding resolver** (`combat::pickup::resolve_item_definition_facts`): a pure
   function `&CanonicalReferencePlayableContent, &item_mint::TypedDefinitionRef ->
   Result<ItemDefinitionFacts, PickupContentError>`. It looks the identity up in
   `content.definitions`, requires a `ReferenceDefinitionKind::Item`, and maps
   `stack_class`/`semantics.container`/`semantics.equipment` into
   `durability::item_transfer::ItemDefinitionFacts` exactly as D82/D83/§6.2 define them
   (unknown stack class and missing/ambiguous definitions both fail closed). This is the part
   B3-1 explicitly deferred: "definition facts come from the caller... Binding them to the
   current Content belongs to B3-2."
3. **Pickup composition** (`combat::pickup::settle_ground_pickup`): given a
   `GroundPickupRequest` (command, source item id, the source's claimed
   `TypedDefinitionRef` identity, destination) and a `DurabilitySession` (mirrors
   `combat::death_reward`'s pattern), it resolves the source item's facts from Content: for
   `MainBackpack` it first reads the character's current backpack through the already-proven
   `read_character_backpack`, resolves *that* slot occupant's facts from Content too, then
   calls `freeze_item_transfer`/`commit_item_transfer` with content-resolved facts only. The
   caller never supplies `ItemDefinitionFacts` directly; it only names which item it means to
   pick up.
4. **Wiring**: `combat_pickup` is a new **top-level** crate module (`lib.rs`, `#[path =
   "combat/pickup.rs"]`), not `combat::pickup`. `combat.rs` is recompiled standalone in
   Content-free contexts (`foundation/mod.rs`'s `#[cfg(test)] mod exact_actor_test_combat`, and
   PG binaries reusing `foundation`), so nesting `crate::content` inside `combat.rs` would force
   all of those to also carry a local `content` module (confirmed: `cargo clippy --all-targets`
   broke on the first attempt, passed clean after moving `pickup.rs` out). `combat_pickup` reaches
   `combat::death_reward::DurabilitySession` through `combat`'s own `pub(crate)` re-export. Same
   D2a/D2b posture otherwise: no production caller yet (GAME-INTERACTION's dispatch is later).
5. **Tests**: unit tests for the resolver (found/not-found, wrong family, unknown stack class,
   proven stack maximum, container capacity, equip pattern true/false), plus PG cases reusing
   `item_transfer_postgres_cases.rs`'s harness (`Database`/`register`/`seed_character`/
   `Harness`) that MINT Ground items from a small fixture `CanonicalReferencePlayableContent`
   and drive `settle_ground_pickup` end to end: a fresh pickup into the empty container slot,
   a pickup into a free backpack entry, and a fail-closed refusal when the claimed item has no
   Content definition. B3-1's own PG suite already proves the D80-D83 admission/merge matrix;
   B3-2's tests prove only the new content-binding layer.
6. **No new migration, no new resource-limit rows**: B3-2 adds no table, no new participant/
   work-unit/byte ceiling; it only resolves values `item_transfer.rs` already bounds
   (`GAMEITEM01-STACK-QUANTITY-MAX`, `-CONTAINER-ENTRIES-MAX`, `-PLACEMENT-DEPTH`,
   `-REACHABLE-ITEMS`, all registered by B3-1).
7. Excluded: D111-D113 (loot inside a corpse container, killer-only window, corpse decay,
   later slice D3), B3-3 weight, `runtime_actor_carrier.rs`, `owner_timer.rs`, any `ai` module,
   and GAME-INTERACTION's actual network dispatch (no production caller yet, same as D2a/D2b).

## Outcome

`combat_pickup::settle_ground_pickup` picks a live Ground item up into the character's
CharacterEquipment `container` slot or the equipped main backpack, resolving both the moved
item's and (for `MainBackpack`) the equipped backpack's `ItemDefinitionFacts` — stack class,
container capacity, `container`-slot equip pattern — from the current
`CanonicalReferencePlayableContent` generation rather than trusting caller-supplied facts, then
commits through B3-1's `freeze_item_transfer`/`commit_item_transfer`. The backpack content
record `oteryn:item.registry.i00002752` now declares the real container-slot equip pattern
(D114), so a real Content generation (not only the B3-1 test fixture) admits it.
