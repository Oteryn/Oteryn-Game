## Outcome

ADR-0020 section 4 asks for a minimal 2D tile and sprite batch on the existing `WindowsRenderer`
and for the shipped placeholder assets to live in a production-owned workspace member with
synthetic or legally approved content only. This task adds exactly that and nothing for N3, N6 or
the entry gate.

- `crates/renderer/src/batch.rs` (GPU-free): `AtlasImage` (RGBA8 square cells, row-major cell
  index, normalized UV rect), `TileView` (the single tile/screen conversion: `tile_to_screen`,
  `screen_to_tile`, `contains`, `viewport_px`), `TileBatch` (one quad per tile, row-major),
  `SpriteBatch` (one tile-sized quad per sprite, culled outside the view, bounded), `QuadInstance`
  (32 bytes: position, size, uv) and `instance_bytes`. Bound: `MAX_BATCH_QUADS` = 16384 per batch.
  Vertex count is `quads * VERTICES_PER_QUAD` (6).
- `crates/renderer/src/scene_gpu.rs` and `windows.rs` (Windows only): one instanced-quad pipeline
  (WGSL, nearest sampling, alpha blending) draws tiles then sprites in one draw call.
  `WindowsRenderer::set_atlas` installs the atlas and `render_batches` draws a frame. `render`
  keeps its clear-only behaviour. Scene resources are built lazily and rebuilt if the surface
  format changes. `render_batches` without an atlas returns `RendererError::Validation`.
- `crates/placeholder-assets` (`oteryn-placeholder-assets`, production, no dependencies): a
  64x32 RGBA atlas generated by integer code (four terrain cells, player, creature, other player,
  target ring). It embeds no binary file and no third-party bytes; see `LICENSE-ASSETS.md`.
- `apps/client/src/scene.rs`: `PlaceholderScene` builds a fixed 15x11 tile grid and three sprites
  from the atlas. `windows_shell` installs the atlas and draws the scene. The window title, the
  fail-closed entry and `GameplayAvailability::PreNativeProtocol` are unchanged.

## Architecture and source of truth

- `PROVEN`: ADR-0020 sections 4 and 7 (N2 row: "Renderer primitives: tile and sprite batch;
  production-owned placeholder asset member"); `crates/renderer` and `ResourceCache`;
  `workspace-boundaries.toml`; `LICENSE-ASSETS.md`.
- Placement: the #162 allocation text said `apps/client`. ADR-0020 places the batch on
  `WindowsRenderer` in `crates/renderer`; the ADR governs and the coordinator confirmed it. The
  client keeps only the placeholder scene composition.
- New member name `oteryn-placeholder-assets` is ADR-0020's UNKNOWN name resolved for this
  member; it contains none of the forbidden fragments.
- Renderer and asset crates carry no protocol, identity or Platform types. `TileCoord` is an opaque
  grid position, not a `WorldId`, `ChannelId` or protocol coordinate.
- `wgpu` is enabled with the existing `wgsl` feature (same pinned version 30.0.0, no new crate and
  no `Cargo.lock` change beyond the new member). The workspace `wgpu` entry had no shader
  front-end, and the only alternative, pass-through shaders, is `unsafe` and forbidden by the
  workspace lints. `rust-dependency-delta.json` records the feature.

## Interfaces N3 and N6 build on

- N3: `TileView::screen_to_tile(x, y)` maps a window pixel to a tile or `None` outside the view.
- N6: `SpriteBatch::push(view, atlas, tile, cell)` places one sprite on a tile and reports culling;
  `clear()` reuses the batch each frame.
- Both consume `PlaceholderCell::index()` or later real art through the same `AtlasImage`.
