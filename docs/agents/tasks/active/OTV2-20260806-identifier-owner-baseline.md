## Delivered owner decisions

### Durable identity

- Independently addressable semantic entities owned by Oteryn-v2 that cross process, service, GameNode, protocol, persistence, durable-event, audit, migration, backup or recovery boundaries default to strongly typed UUIDv7.
- Cross-repository and externally owned identifiers adopt UUIDv7 only through their authoritative contract or an accepted coordinated migration.
- UUIDv7 is identity, not a bearer secret, capability, ordering value or proof of current authority.
- Raw UUID values are not interchangeable in domain APIs; distinct strong types and scope wrappers are mandatory.
- Nil UUID is not a valid entity or sentinel; absence is represented explicitly.
- Durable IDs are immutable, never reused and generated by their authoritative domain owner without a central UUID service.
- Duplicate insertion or collision never overwrites an existing entity.

### Runtime, protocol, content and sequencing

- Serialization or GameNode transfer does not make every nested runtime object an independent durable entity.
- Nested state may cross boundaries inside a fenced aggregate snapshot using aggregate-local references when it has no separate lifecycle or external reference.
- Hot simulation state uses runtime-local generational handles.
- Frequent gameplay traffic uses compact session-local handles after authoritative identity establishment.
- Ticks, sequences, revisions, generations, fencing tokens and offsets are scoped numeric values, defaulting to `u64`-class representation.
- Static content uses stable content keys, content revisions and compact bundle/runtime IDs.
- Tiles, coordinates, chunks, pathfinding nodes, transient effects and per-tick work do not receive UUIDv7 automatically.
- PostgreSQL native `uuid` and full 128-bit binary protocol preservation are accepted baselines for adopted UUID identities.
- Internal UUIDv7 values are not automatically public references because their time component may disclose approximate creation time.
- Capacity planning benchmarks the accepted hybrid rather than UUIDv7 in every hot path.

### Topology, instance and social semantics

- `WorldId` globally identifies one logical world.
- Canonical channel, instance and party identities are `WorldId + ChannelId`, `WorldId + InstanceId` and `WorldId + PartyId`.
- Globally collision-resistant representation does not erase semantic scope.
- Channels remain the primary persistent-world topology; instances are isolated optional contexts within one world and economy.
- One authoritative `InstanceRuntime` owns participants and instance-local simulation.
- Same-world players from multiple channels may be admitted directly into one instance through the shared activity-admission engine.
- Entry and exit use generation-fenced, idempotent ownership transitions with validated origin-channel return metadata.
- Cross-GameNode transition uses make-before-break handoff and preserves ADR-0003: Gateway remains control plane rather than gameplay proxy.
- Rewards, lockouts and inventory mutations settle authoritatively and idempotently before cleanup.
- Exact channel, instance, node and map placement are non-public; contact/VIP and account-wide friendship require explicit mutual consent, and alternate characters remain hidden by default.
