## Outcome

Forge dust exists as a durable Character asset (IMBUE-FORGE-0 §9, stored as BANK-0 §3):
`game_character_forge_dust` (balance 0 to `dust_limit`, limit 100-225, initial 100) and the
immutable `game_character_forge_dust_entries` ledger, chained by `previous_entry_id` with the
balance row naming its latest entry. The writer exposes a `SPEND` API with the closed cause
`Proficiency` (reserved for PROF-SHAPE-1b) and a `GAIN` writer with the closed cause
`CreatureKill` (reserved for FORGE-CREATURE-1); both run inside the caller's transaction and
write no receipt, `ForgeCause` or history. Production wires neither. A read-only ledger audit
walks the chain and reconciles credited minus spent against the balance.

## Architecture and source of truth

- `PROVEN`: architect batch `ARCH-BATCH-TIMED-FORGE-PROF-PACKETS-V1` §1.3 and §2.1 (#1687);
  IMBUE-FORGE-0 §9 and §15 (`IMBFORGE0-RL-08`); BANK-0 §3 and §7.2; composition decision rules 1
  and 4.
- `DERIVED`: the ledger stores the caller's cause occurrence, TransactionId and `created_xact_id`
  so PROF-SHAPE-1b's deferred guard can tie its `SPEND` to its receipt; one entry per (Character,
  cause occurrence). `CONVERT` and `LIMIT_RAISE` are in the kind domain but refused by the
  cause/arithmetic CHECKs until FORGE-1b replaces them.

## High-risk authority/recovery qualification

Persistence of a new value asset. The writer re-takes the caller's `character_root` lock (rule 4)
and checks the fenced World before it locks the dust row; it never commits. No session, lease or
generation authority is interpreted beyond the caller's fence.

## Acceptance criteria

- [x] Balance within 0 to `dust_limit`, `dust_limit` within 100-225 (CHECKs; 100 and 225 accepted,
  99 and 226 rejected).
- [x] One ledger entry per balance change in the same transaction, chained; deferred guards refuse
  a balance without an entry, an entry without the row update, a broken link, a second first entry
  and a row pointing to an older entry.
- [x] Entries immutable (no UPDATE, DELETE or TRUNCATE); the runtime never deletes; grants as
  BANK-0 §3.
- [x] A gain above the limit credits up to it and records the lost part.
- [x] A `SPEND` above the balance is refused before any write (no zero row either).
- [x] Lock order: rule 4's root lock, then the dust row; a concurrent spend and gain serialize.
- [x] `IMBFORGE0-RL-08` registered; DUR-03 §18 and composition rule 1 amendments.
- [ ] Independent persistence and economy review (Codex) on the frozen head (control plane).
