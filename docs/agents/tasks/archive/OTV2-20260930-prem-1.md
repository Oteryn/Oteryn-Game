## Outcome

PREM-1 was split for size: this PR is **PREM-1a**.

- Migration 0029: the durable consumer fence. It has an immutable evidence log keyed by
  (account, `authority_revision`) with semantic fingerprints, which is the equivocation horizon;
  an account high water with a sticky conflict marker; and an (account, entitlement) lifecycle
  high water. Triggers only let the fence advance.
- `durability::premium_fence`: fences one snapshot per transaction. The outcome is accepted,
  replayed, stale or conflict.
- `premium::snapshot`: validates `oteryn.premium_snapshot.v1`, including the nonce and account
  binding, the compatibility record and the lease bound.
- `premium::PremiumConsumer`:
  - classifies per consumer §8;
  - applies `premium-surfaces-1` (`REQUIRE_CURRENT` everywhere);
  - provides `premium_current` and `premium_entitlement_ended`;
  - re-proves authority after a restart before any benefit.

**PREM-1b**, which needs a fresh allocation, covers the mTLS snapshot client, nonce generation,
refresh scheduling and the in-process test producer. It is blocked on the request side of
PREMIUM-DELIVERY-0 §3 (the escalation on #162).

## High-risk authority/recovery qualification

`AuthorityInvariant × ConsumerBoundary × MutationOperator` for the one boundary, fence then
authorize:

- **Identity and binding.** Tested: another account, another nonce, and another entitlement
  (which opens its own row). `NONE` requires a null entitlement.
- **Liveness and authority.**
  - Tested: stale revision; delayed older ACTIVE after REVOKE or NONE; replay; equivocation at
    the current and at a historical revision; lifecycle regression; restart before re-proof;
    quarantine on a fence write failure (unit, `INVALID_OR_CONFLICTING`).
  - Time-derived state under one `lifecycle_revision` (NOT_YET_EFFECTIVE -> ACTIVE -> EXPIRED)
    is accepted, while another product, entitlement, effective window or revocation under it
    is a conflict. The same authority revision with another state is still equivocation.
  - A future version that adds members is Unsupported when bound and Malformed when unbound;
    a missing or ill-typed compatibility member is Malformed.
  - The old grant after NONE without a new lifecycle revision is a conflict; a re-grant with a
    higher lifecycle revision is accepted.
  - EXPIRED -> ACTIVE and ACTIVE -> NOT_YET_EFFECTIVE under one lifecycle revision are
    conflicts.
  - Concurrent first insert: fails closed through a unique violation.
- **Temporal and provenance.**
  - Tested: conservative start and end; lease cutoff; the commercial end before the lease;
    unsynchronized time; lease above policy; unknown schema, product, version or profile.
  - Build provenance and `refresh_after` are excluded from the fingerprint.
- **Durable guards.** Tested: lowering, conflict clearing, delete and truncate are rejected, and
  the runtime-role grants are checked.

## Review repair (control-plane FIX of `c22a825b`)

- **MEDIUM, fixed.** A time-derived state is no longer a lifecycle fact. The lifecycle
  fingerprint covers the product, the entitlement, `effective_from`/`effective_until` and
  whether the state is `REVOKED`. The full state stays in the per-revision evidence
  fingerprint. The state of the newer snapshot, by `authority_revision`, wins, so
  NOT_YET_EFFECTIVE -> ACTIVE -> EXPIRED without a `lifecycle_revision` bump no longer marks the
  account conflicting.
- **LOW, fixed.** A fence write failure quarantines the account as `INVALID_OR_CONFLICTING`
  (consumer §6.4: the fence itself is unsafe), no longer `AUTHORITY_UNAVAILABLE`. Both deny.
- **Stated interpretation.** A higher `authority_revision` with a lower `lifecycle_revision` is a
  conflict, not stale. This is stricter than consumer §6.2. It follows PREMIUM-DELIVERY-0 §8.1
  step 4: `authority_revision` is monotonic per account, so a newer authority that goes back on
  an entitlement's lifecycle contradicts accepted evidence.
- **Codex P1 on `71f01c11`, fixed.** Revocation stays a lifecycle fact: PREMIUM-DELIVERY-0 §4
  raises `lifecycle_revision` with each revocation change. REVOKED -> ACTIVE (or ACTIVE ->
  REVOKED) under one lifecycle revision is a conflict, so benefit is not re-authorized.
- **Codex P1 on `71f01c11`, fixed (supersedes the earlier `deny_unknown_fields`
  interpretation).** A bound response with a future `schema`, `product_id`, `product_version`
  or `producer_profile` is Unsupported even when it adds members. The binding and the
  compatibility record are read from the untyped member map before the strict parse. Unsupported
  denies at once, whereas Malformed would have left a current ACTIVE until lease expiry. An
  unbound response stays Malformed and changes nothing.
- **Codex P1 on `5cca6faf`, fixed.** An entitlement that a later accepted snapshot withdrew
  (`NONE` or another entitlement) reopens only with a strictly higher `lifecycle_revision`. A
  grant needs a new lifecycle revision (PREMIUM-DELIVERY-0 §4), so the old grant replayed
  after NONE is a conflict. The check reads the never-deleted evidence log under the account
  row lock, so no schema change is needed.
- **Codex P1 on `8e46d064`, fixed (root cause of the three fence rounds).** The fence now
  encodes the whole state machine for one lifecycle revision. The state may only move as
  elapsed time does, NOT_YET_EFFECTIVE -> ACTIVE -> EXPIRED. A step back (EXPIRED -> ACTIVE,
  ACTIVE -> NOT_YET_EFFECTIVE), entering or leaving REVOKED, or reopening a withdrawn
  entitlement is a conflict and needs a new lifecycle revision (PREMIUM-DELIVERY-0 §4). The
  stored state comes from the entitlement fence's latest evidence row, so no schema change is
  needed.
- **Codex P2 on `5cca6faf`, fixed.** A bound response with a missing or ill-typed `schema`,
  `product_id`, `product_version` or `producer_profile` is Malformed and changes nothing. Only
  a present, well-typed value outside the compatibility record is Unsupported.
- `main` (with #1393, migration 0030) was merged in with a merge commit; both `mod` includes are
  kept in `character_authority_postgres.rs`.
