## Outcome

After admission the client builds a placeholder view from the JoinSnapshot (own position, `world_object_overlay` markers) drawn with the existing TileBatch and SpriteBatch. ClickWalk and arrow keys call `Session::step_retrying`; the step outcome and domain-1 and domain-2 deltas move the view. Any session error returns to login with `PublicClass::SessionUnavailable`. No new protocol, map loading, or creature/chat rendering.

Extensions beyond the packet's owned paths:

- `crates/session/src/lib.rs` (control-plane approved): re-export of the step and overlay types and `CommandStatus`, because the client may not depend on protocol-oteryn (ADR-0020).
- `apps/client/src/lib.rs`, `main.rs` (control-plane approved): `ClientBootstrap::start_play` (spawns the session task on the client runtime), `AdmittedSession::play_view`, and `native_entry` returning the client with the admitted session so the winit shell can drive the session on the runtime its stream is bound to.

Codex review fixes: the session task (`play::run_session`) runs on the client runtime and keeps servicing liveness while idle; the shell only polls a channel and never waits on the network; a session end returns to the pre-admission placeholder scene with the public class in the title and console (the process keeps running; a new login attempt is not wired here); overlay entries are kept for every floor and the drawn markers are refiltered by the current floor.

Repair round 2: the session task drains `Session::take_events` after every step and idle serve slice and forwards the pushed domain-1 and domain-2 deltas to the view, so the 256-event queue cannot overflow; main merged in.

Repair round 3: the semantic placement `oteryn:cell/entry-door` the server emits draws a marker (a placeholder cell table until map loading); the session-to-shell channel is a bounded coalescing mailbox (latest own position, latest entry per placement capped at 1024, one step outcome), so an undrained shell holds bounded memory.

`windows_shell.rs` cannot be compiled on the Linux worker (no mingw for aws-lc); it was checked by reading and is covered by Windows CI.
