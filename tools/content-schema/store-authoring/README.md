# Store offer authoring schema candidate v1

Ownership decision: [`docs/architecture/OTERYN_STORE_CATALOG_OWNER_DECISION_2026-09-28.md`](../../../docs/architecture/OTERYN_STORE_CATALOG_OWNER_DECISION_2026-09-28.md).

The in-game Tibia Store catalog (categories, offers, prices, product references) and
delivery of a purchase to the character (store inbox). Modeled on
`../spell-authoring/` as the lean authoring-package template. The player's Tibia Coin
balance, payment and purchase ledger are Platform's, not modeled here.

## Engine model

Canary (`data/modules/scripts/gamestore/catalog/*.lua`, 22 files, version 2.0, 27 offer
types) and Crystal (`data/modules/scripts/gamestore/init.lua` + `gamestore.lua`, version
1.1, 28 offer types) both define a `category {name, parent, icons, rookgaard, state,
offers[] | subclasses[]}` / `offer {name, price, itemtype, count, charges, type,
description, icons, id, sexId, addon, blessid, home, number, validUntil, ...}` model.
Canary (actively maintained) is the primary content source for the authored catalog;
Crystal is read for cross-engine verification only (`store_census.py`), never merged in.
`store_constants.py` documents every `GameStore.OfferTypes` member's per-engine numeric
id, product-payload kind, and the two engines' numbering/spelling differences
(`weekly_task_expansion` is Canary id 25 / Crystal id 28; Crystal alone defines an unused
`hunting_slot`, id 25).

| File | Purpose |
|---|---|
| `lua_lite.py` | A small, strict tokenizer/parser for exactly the Lua table-literal shapes the GameStore sources use (never a Lua interpreter); an unrecognized top-level shape is a hard parse error. `if`/`for`/`function` blocks (config-dependent branches, engine bootstrap) are skipped and recorded, never evaluated. |
| `store_constants.py` | Canonical `offer_type`/`state`/`coin_type` vocabulary, each entry's per-engine numeric id and product-payload `kind`, with every cross-engine divergence documented in place. |
| `item_bindings.py` | Loads `imports/crystalserver/bindings/items.json` (both engines share the one Crystal item id space) fail-closed; a store-package-local copy of `item-authoring/engine_items.py::build_identity_index`'s loader, not an import of that module. |
| `build_formal_schema.py` | Source of `store-offer.schema.json`; regenerates it. |
| `store-offer.schema.json` | Categories + offers, JSON Schema 2020-12, closed shapes; shares `key`/`revision`/`identity`/`ItemRef` with `../monster-authoring/monster.schema.json`. |
| `convert_store.py` | Parses the pinned engine sources (digest-verified, `EXPECTED_DIGESTS`) into `{catalog, conversion_report}`. Unresolved item refs and offer_type/non-literal `id` fields are reported, never invented; such an offer is excluded from `catalog.offers` only when its product reference cannot be built at all. |
| `test_convert_store.py` | Converter fixture tests against a tiny synthetic checkout (item identity still resolves against the real committed bindings). |
| `validate_store.py` | Schema plus semantic checks: unique category/offer keys, category parent/shape consistency, offer category resolution, offer_type ↔ product.kind consistency, item quantity (`count` xor `charges`). |
| `verify_formal_schema.py` | Positive/negative fixture cases; regenerates `synthetic-valid-store-offer.json`. Each negative asserts its expected error fragment. |
| `store_census.py` | Per-engine counts (categories, offers, offers per type/product kind, item refs resolved/unresolved) and a cross-engine difference summary (category/offer set diffs, offer-type count deltas, numbering/coin-type-default divergence). `--check` regenerates in memory and diffs against the committed samples; `--self-check` asserts exact known offers. |
| `samples/store-census-canary-47dfd51f.json` | Canary census (includes the cross-engine diff). |
| `samples/store-census-crystal-ff7ede5.json` | Crystal census (includes the cross-engine diff). |
| `synthetic-valid-store-offer.json` | Small hand-built valid catalog (not transcribed from either engine); regenerated by `verify_formal_schema.py`. |

```text
pip install -r requirements.txt
python build_formal_schema.py && git diff --exit-code -- .
python verify_formal_schema.py
python validate_store.py synthetic-valid-store-offer.json
python test_convert_store.py

python store_census.py --canary <canary@47dfd51f> --crystal <crystalserver@ff7ede5>
python store_census.py --canary <canary@47dfd51f> --crystal <crystalserver@ff7ede5> --check --self-check
```

## Product reference payload by offer_type

`item` (stackable/house/item_bed/item_unique/charges): `item_refs` (Oteryn `Item` keys,
resolved through the Crystal id space) + exactly one of `count`/`charges`. `outfit`:
`female_look_type`/`male_look_type` + `addon`. `mount`: `mount_id` (the engine `id`
field). `hireling`: `female_look_type`/`male_look_type`. `blessing`: `bless_id` + `count`.
`blessing_bundle` (allblessings): `count` only. `premium_time`: `days` (`validUntil`).
`hireling_typed` (hireling_skill/hireling_outfit): `typed_id`, always `null` — the source
`id` is `HIRELING_SKILLS.*`/`HIRELING_OUTFITS.*`, a lookup table this reader cannot
statically resolve; an explicit, documented omission, not a silent drop. Every other
offer_type is `service` (no payload).

Cross-cutting offer fields not tied to a product kind: `home` (bool, uncertain precise
client semantics beyond being an engine-recognized flag, passed through verbatim),
`hireling_slot_number` (engine `number`, always 1 in observed data, passed through
verbatim), `engine_offer_id` (the engine `id` for every offer_type except `mount`, where
it is the payload itself; a legacy/incidental store action id, never used for identity).
Canary's own catalog is inconsistent for one `charges`-type offer ("Ultimate Health Keg",
itemtype 25906), which sources its use-count from `count` instead of `charges`; the
converter accepts either.
