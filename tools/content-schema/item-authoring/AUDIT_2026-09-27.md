# Independent audit of Item authoring candidate v4

Date: 2026-09-27

Repository: `Oteryn/Oteryn-Game`

Pull request: [#952](https://github.com/Oteryn/Oteryn-Game/pull/952)

Audited implementation head: `56a39d1587c31023561b04c4ad87644bc806b094`

Audit scope: authoring schemas, evidence/validation boundary, engine converter,
population census, reproducibility, package checks and repository lifecycle state.

## Verdict

**Do not freeze or merge the audited head.**

The schema and validator are substantially stronger than the previous candidate and
their focused suite passes. The remaining problems are not a reason to discard the
design. They are, however, material enough that the current head cannot be treated as
a reproducible, independently qualified candidate:

1. the converter assigns an explicit Delivery Task decision to every Canary item
   without reading Canary's Task Board pool;
2. the pinned-source digest gate rejects valid Windows checkouts of both upstream
   repositories because Git line-ending conversion changes the working-tree bytes;
3. repository CI does not execute this package, so the green PR checks do not prove
   the focused validation claimed in the PR;
4. the stated Ruff format result is not reproducible with the available Ruff version;
5. the census `--self-check` does not establish the claimed deterministic regeneration
   for both engines.

Items 1 and 2 are **material blockers**. Items 3-5 are qualification/evidence gaps
that should be closed before the next freeze. The audit did not change implementation
or source data.

## Evidence model

- **PROVEN**: observed directly in the audited Git tree, an exact pinned upstream
  checkout, a command result or current GitHub state.
- **DERIVED**: follows from multiple proven observations but is not itself directly
  emitted by one source.
- **UNKNOWN**: not established by the available evidence.

## Findings

### F-01 — Material blocker — Canary Delivery Task values are fabricated exclusions

Classification: **PROVEN**

Severity: **High**

The accepted architecture defines `delivery_task_eligible` as a required,
author-owned decision: `true` admits an Item definition to a future pool and `false`
explicitly excludes it. The same document identifies Canary Task Board settings and
Crystal's delivery list as distinct upstream evidence sources.

The converter does something narrower and semantically unsafe:

- `engine_items.py:1194` loads delivery IDs only when `engine == "crystal"`; Canary
  receives an empty set;
- `engine_items.py:1320` writes the required boolean from membership in that set;
- `engine_items.py:1326-1330` labels every non-member, including every Canary item,
  `not_in_crystal_delivery_list`;
- the committed Canary census therefore reports all 11,606 converted candidates as
  `not_in_crystal_delivery_list`;
- the validator sees a syntactically valid boolean and cannot distinguish a genuine
  author decision from this fallback.

This means absence of Crystal-only evidence is converted into an explicit Oteryn
exclusion for a different engine. That contradicts the documented meaning of `false`
and the closed evidence discipline used by the six authored examples.

The Crystal mapping also needs a clearer boundary. Membership in Crystal's list is
useful source evidence and a proposed authoring value, but it is not automatically an
Oteryn author decision unless an explicit adoption rule is accepted and recorded.

Required repair:

1. parse and digest-pin the relevant Canary Task Board pool instead of substituting an
   empty Crystal set;
2. keep upstream observation/proposal separate from the final author-owned boolean;
3. do not emit a schema-valid explicit `false` when the decision is unresolved;
4. require an admitted authoring rule or per-item decision before a bundle is called
   import-ready;
5. add negative regressions proving that missing/other-engine pool evidence cannot be
   normalized to explicit ineligibility.

The final portable Item should still contain only the requested boolean. Source basis,
conflicts and unresolved state belong in the evidence/readiness report, not in runtime
Item data.

### F-02 — Material blocker — Source digest verification is not Windows-reproducible

Classification: **PROVEN**

Severity: **High**

Both pinned upstream repositories were checked out at exactly the revisions declared
by the package:

- Canary `47dfd51f45280a59a1d3e50ba7edd573d7234446`;
- Crystal `ff7ede593c69d4c658b382c97443e8155926924a`.

Both checkouts use `core.autocrlf=true`. The expected SHA-256 values in the package
match the LF-only Git blobs, while `sha256_file()` hashes raw working-tree bytes. The
normal Windows checkout therefore fails before conversion starts.

Observed values:

| Artifact | Working-tree SHA-256 | Pinned/Git-blob SHA-256 | Result after CRLF to LF normalization |
|---|---|---|---|
| Canary `data/items/items.xml` | `8ab96442cb8ca4bc45be2d95786bb753c0791245c5013c9aac59e5643668e62a` | `1cf2992cdd7cc5b97bcf930b8c89676ec1627170008e995fd2576110e26022f2` | exact match |
| Crystal `data/items/items.xml` | `d844571e7456782ffa6d6fb404f91d9ac75baf326fcb834f26406a881f7124fb` | `c847293e980b40ec146e2b7f68a62366513a1c0566d16b7c3a011136087021eb` | exact match |
| Crystal delivery list | `dd597fe2648e40439ab3276527b69e1aae4b71b975aee7c2b80495eacabf3710` | `7b30362470893f6e3ce6bdc0237ac5d3f13d6e5288ce10591a93fde2013b688d` | exact match |

The Canary XML contained 85,286 converted CRLF sequences, the Crystal XML 88,107,
and the Crystal delivery list 459. The binary `appearances.dat` files matched their Git
blobs exactly and must not be text-normalized.

As a result, both exact-source census commands exit with a digest mismatch on the
owner's normal Windows environment. This disproves cross-platform reproducibility of
the current command contract; it does not indicate that the pinned source revisions
are wrong.

Required repair:

1. define the digest domain per artifact: canonical Git blob/archive bytes for text,
   raw exact bytes for binary artifacts;
2. either read the pinned Git object directly or perform an explicit, narrowly scoped
   newline normalization for declared text artifacts before digesting and parsing;
3. record the digest mode alongside each artifact digest;
4. test LF and CRLF checkouts and prove identical parsed output/bundle digest;
5. continue to reject all other byte/content changes.

Blind normalization of all files is not acceptable because protobuf/binary artifacts
may legitimately contain the byte sequence `0d 0a`.

### F-03 — Qualification gap — Green PR CI does not execute the Item package

Classification: **PROVEN**

Severity: **Medium-high**

At audited head `56a39d15`, current GitHub checks were green, including governance,
architecture audit, CodeQL and `game-gate`. The PR description itself states that
repository CI does not execute this package. Therefore those green checks do not prove:

- generated-schema byte determinism;
- the 234 focused schema/validator checks;
- CLI behavior with the pinned Python dependencies;
- converter/census behavior;
- Ruff formatting.

Required repair: add a changed-path CI lane, or an equivalent required repository test,
that installs `requirements.txt` in a clean environment and runs at minimum:

1. generated-schema regeneration plus a clean diff check;
2. `verify_formal_schema.py`;
3. the positive CLI fixture;
4. Item Master validation/tests affected by this contract;
5. pinned Ruff check and format check;
6. converter tests covering LF/CRLF source text and both engine delivery-evidence paths.

The whole upstream census may remain a separately reproducible evidence job if cloning
the two pinned repositories is intentionally too expensive for every PR, but its
fixture-level semantics must still be exercised in CI.

### F-04 — Qualification gap — Ruff format PASS claim is not reproducible

Classification: **PROVEN**

Severity: **Medium**

With Ruff `0.16.1`:

- `ruff check tools/content-schema/item-authoring` exits 0;
- `ruff format --check --diff tools/content-schema/item-authoring` exits 1;
- `verify_formal_schema.py` would be reformatted in two locations (around lines 676 and
  2773 of the audited file).

No Ruff version is pinned by this package, while the PR description claims both check
and format pass. Either format with the repository-selected Ruff version or pin and
document the exact accepted version. The claim should then be regenerated from a clean
environment.

### F-05 — Qualification gap — Census self-check is asymmetric and not a regeneration check

Classification: **PROVEN**

Severity: **Medium**

`population_census.py --self-check` currently:

- explicitly skips all assertions for Canary (`population_census.py:64-71`);
- checks six selected Crystal IDs and a few Magic Sword values
  (`population_census.py:72-87`);
- writes the requested census before the self-check;
- does not compare the newly generated bytes or digest to the committed census file.

The tool can still generate deterministic JSON, but this command alone cannot establish
the PR claim that both committed censuses regenerate byte-identically.

Required repair:

1. add engine-specific semantic assertions for Canary;
2. compare generated output against a previously read committed artifact, or generate
   to a temporary path followed by an exact diff;
3. run the check for both engines after the digest portability repair;
4. fail rather than print `skipped` when `--self-check` was explicitly requested and no
   checks exist for that engine.

### F-06 — Lifecycle evidence is stale relative to the live PR head

Classification: **PROVEN**

Severity: **Medium**

The active task record still checkpoints `517daa6b...`, says the owner must select the
v4 repair branch, leaves final head/CI pending, and does not cover the converter/census
commits now on PR head `56a39d15...`. The PR is correctly still marked draft and its
description correctly says the current head is not frozen. There are no submitted PR
reviews on the audited head.

This is not an implementation defect, but it prevents a valid freeze/closeout claim.
After material repairs, update the task record and programme mirror from fresh GitHub
state, bind the exact successor SHA, and perform fresh candidate-specific validation
and independent review. Evidence for `517daa6b...` or `56a39d15...` must not be reused
as exact-head qualification for a repaired successor.

### F-07 — Scope/risk observation — Converter and whole-population census expand the slice

Classification: **DERIVED**

Severity: **Advisory**

The converter and two census artifacts are useful evidence, but they materially expand
the original formal-schema slice and introduce source checkout, digest, identity,
classification and Delivery Task normalization behavior. This explains why the two
high-severity findings were not caught by the schema-only tests.

Before the next freeze, explicitly choose one of two coherent paths:

- retain converter/census in #952, extend its acceptance and CI accordingly; or
- keep #952 focused on the formal authoring contract and move population conversion to
  a linked follow-up after the schema is accepted.

The audit does not require a split; it requires that the added behavior receive tests
and acceptance proportional to what it now claims.

## Verified strengths

The following checks passed and should be preserved:

- clean isolated environment installed all three pinned requirements;
- `verify_formal_schema.py`: **PASS 234/234**, covering 13 templates;
- the positive CLI fixture returned `valid=true` and only the expected unresolved
  raster-atlas warning;
- missing `rfc3339-validator` causes verifier/CLI exit code 1 rather than a fail-open
  validation result;
- Item Master validation: **71 fields, 50 families, 22 profiles, 0 unassigned**;
- Item Master tests: **2 positive and 5 negative** cases pass;
- governance validation: **22 policy documents and 9 lanes** pass;
- lifecycle tests: **13/13** pass;
- generated files were content-clean after regeneration; apparent Windows modifications
  were index/stat/line-ending presentation, with no Git content diff;
- Ruff static check passes;
- current GitHub governance, architecture, CodeQL and merge-gate checks pass;
- auxiliary schemas reuse canonical `$defs` instead of copying them;
- canonical identity binding, dependency closure, presentation evidence and negative
  validation are materially stronger than the previous candidate;
- the README correctly limits the package to authoring/evidence and does not claim
  runtime lowering, corpus migration, gameplay parity or production activation.

These passes prove the bounded schema/validator behavior stated above. They do not
override F-01/F-02 or promote the package to runtime/Global parity.

## Recommended repair and requalification order

1. Return explicitly to AUTHORING; keep PR #952 draft.
2. Repair Delivery Task evidence/decision separation for both engines (F-01).
3. Repair per-artifact digest portability without weakening binary verification (F-02).
4. Add Canary and deterministic-output census checks (F-05).
5. Pin/standardize Ruff and format the package (F-04).
6. Add package CI or an accepted required equivalent (F-03).
7. Decide whether converter/census stays in this PR and update acceptance accordingly
   (F-07).
8. Regenerate both censuses from exact pinned sources on Windows and at least one LF
   environment; require identical semantic results and bundle digests.
9. Update the task/Jira checkpoint only after fresh live-state reads.
10. Freeze the exact repaired remote SHA, then rerun all focused, governance and
    exact-head CI checks plus independent review.

## Acceptance gate for the successor candidate

The successor is ready to freeze only when all of the following are true:

- no engine can turn missing or other-engine Delivery Task evidence into explicit
  `false`;
- both engine pools have a provenance-bound observation path and the final boolean has
  an explicit Oteryn authoring basis;
- exact pinned upstream sources pass digest verification on supported LF and CRLF
  checkouts without normalizing binary bytes;
- both censuses regenerate through a check that fails on byte/digest drift;
- focused schema/validator/converter tests and Ruff check/format run in a clean pinned
  environment;
- repository CI (or a formally accepted required equivalent) exercises the package;
- the task record, PR body and programme mirror all identify the same freshly frozen
  SHA and do not reuse predecessor-head evidence.
